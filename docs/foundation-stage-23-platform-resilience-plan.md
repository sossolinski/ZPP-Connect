# Foundation Stage 23 — Platform Resilience, Recovery & Data Integrity Plan

Status: **APPROVED IMPLEMENTATION BASELINE**

This plan defines technical resilience for the emergency/crisis-response platform. It is
not organisational Readiness, an ERP capability, a training system, or an exercise
management stage. The product boundary is recorded in
[Post-Stage 22 Product Scope Realignment](post-stage22-product-scope-realignment.md).

## 1. Objectives

Stage 23 will make the current PostgreSQL deployment recoverable and will prove recovery
continuously. It will provide operator-safe commands for creating and verifying backups,
restoring into a clean disposable database, checking bounded application invariants,
and retaining only recognized backup pairs. It will also distinguish cheap process
liveness from database-backed technical readiness.

The intended outcome is evidence, not a claim based only on a successful `pg_dump`:

```text
seeded source DB -> custom-format dump + manifest -> checksum/catalog verification
                 -> empty recovery DB -> pg_restore -> migration/domain/integrity checks
```

## 2. Current-state analysis

- Production composition requires `PERSISTENCE_MODE=postgres`; Prisma is the data-access
  layer and 23 ordered migrations define the schema.
- `docker-compose.yml` currently runs PostgreSQL 16 with a named `postgres-data` volume,
  builds a Node 22 API, runs migrations plus the canonical seed, and starts the API. This
  composition is a development convenience, not a production backup scheduler.
- Production API startup requires `DATABASE_URL`, Entra configuration, and deployment
  configuration. The repository does not provision an external database, secrets store,
  job scheduler, alert transport, or remote backup destination.
- `/api/health` is public and process-local. It currently reports the configured
  PostgreSQL production mode without querying the database.
- Generated approved AAR PDFs are exact `BYTEA` values in `AfterActionPdfArtifact`, with
  stored byte length, artifact SHA-256 and source-content SHA-256. They are PostgreSQL
  data and therefore included in a database dump.
- Imports retain source SHA-256 and bounded provenance but intentionally do not retain
  uploaded source bytes. CSV exports retain metadata and hashes but intentionally do not
  retain generated bytes. Neither can be reconstructed from a backup as an original file.
- `DATA_DIR`, `StoredFile`, and disk upload helpers exist for the memory/demo router. The
  explicit PostgreSQL production composition does not mount the legacy disk upload route,
  and Stage 16 proves no production import file is persisted there. The compose
  `app-storage` volume is therefore not a supported production authority. Any deployment
  that has added authoritative files there is outside the verified recovery contract.
- Durable notification outbox/projection state, dictionaries, application configuration,
  roles, permissions, AuditLog and all operational aggregates are PostgreSQL-backed.
- There is no existing backup, restore, retention, recovery rehearsal, scheduler, or
  vendor monitoring implementation in the repository.
- CI uses PostgreSQL 16 and Node 22. Developer tooling inspected for this plan uses the
  PostgreSQL 16 client family. The recovery gate must print and compare native-tool and
  server major versions so version drift does not remain silent.

## 3. Protected assets

The Stage 23 backup boundary is the complete application PostgreSQL database, including:

- incidents/Sessions and crisis casework;
- identities, roles, effective-access configuration and incident assignments;
- groups, rosters, documents, acknowledgements, notifications and audit history;
- operational briefings, imports/exports provenance and mutable dictionaries;
- approved AAR history and exact persisted PDF bytes;
- `_prisma_migrations`, sequences, indexes, constraints and database triggers;
- legacy tables that still coexist with the current product, even though Exercise,
  Training and organisational Readiness are not primary recovery acceptance criteria.

Required recovery inputs outside the dump are: application source/image for a compatible
release, environment and Entra values, TLS/network/DNS/deployment configuration, database
credentials, and the backup artifact plus manifest. They are deployment responsibilities
and are documented in the runbooks. Secrets and infrastructure configuration are not
copied into a backup manifest.

## 4. Backup architecture

Use PostgreSQL `pg_dump` custom format with compression, `--no-owner` and
`--no-privileges`. Custom format is selected because it is portable across ordinary
PostgreSQL deployments, supports a catalog check through `pg_restore --list`, preserves
schema/data objects, and gives `pg_restore` deterministic error handling. Plain SQL lacks
an independently readable archive catalog; directory format adds multi-file lifecycle
and cleanup complexity that is not justified by this repository's current scale.

`npm run backup` will:

1. validate `DATABASE_URL` and an explicit `BACKUP_DIR`;
2. require PostgreSQL native tools and a supported client/server version relationship;
3. write a private temporary archive and atomically publish it only after success;
4. calculate SHA-256 and size;
5. record a versioned JSON manifest with timestamp, archive filename, application version,
   PostgreSQL client/server versions, completed Prisma migrations and critical table counts;
6. omit URLs, passwords and all secret environment values;
7. emit one structured JSON success/failure record and use a non-zero failure exit code.

Directories are created with mode `0700`; artifacts and manifests use `0600`. The files
use controlled timestamp/random names and are never committed.

## 5. Restore architecture

`npm run restore:verify` accepts an explicit manifest and `RESTORE_DATABASE_URL`. It
verifies the backup first, rejects a source/target identity match, requires a target
database with the `zpp_stage23_restore_` safety prefix unless an explicit test-only
override is supplied, and requires that target to have no user tables. It never drops,
truncates, cleans, or overwrites a database.

It then runs `pg_restore --exit-on-error --no-owner --no-privileges` and verifies:

- database accessibility;
- exact completed Prisma migration identities from the manifest;
- recorded critical table counts;
- PostgreSQL constraints are validated;
- application-level hashes and state invariants through the bounded integrity checker.

Database creation/deletion is deliberately outside the restore command. The rehearsal
driver creates and removes only exact, generated disposable database names.

## 6. Recovery verification

The automated recovery gate creates a fresh source database, applies all migrations,
seeds canonical data, and inserts a small Stage 23 fixture containing a REAL closed
Session, Audit history, an approved AAR and exact retained PDF bytes. It then performs
backup, pre-restore verification, clean restore and application verification in a second
database. It checks meaningful rows for Users/Roles, Sessions, Documents, AuditLog,
Dictionaries, AARs and PDF artifacts, including AAR logical and PDF byte hashes.

The gate also alters a copied archive and proves verification fails before restore. A
trap removes only the two generated databases and temporary directory.

## 7. Recovery Point Objective (RPO)

**Project assumption, not a business-approved SLA: 24 hours.** A deployment should run a
successful logical backup at least daily. The repository supplies the command and signal,
not the scheduler. Provider snapshots/WAL archiving may later reduce the RPO, but Stage 23
must not claim point-in-time recovery from logical dumps.

## 8. Recovery Time Objective (RTO)

**Project assumption, not a business-approved SLA: 4 hours.** This covers selecting a
verified backup, provisioning an empty compatible PostgreSQL database, restoring,
verifying, supplying deployment configuration and starting the application. Actual
duration depends on data volume and infrastructure; operators must measure it from
rehearsals rather than treating CI fixture timing as capacity evidence.

## 9. Backup retention

Default project policy is 35 days with at least seven newest complete backup pairs kept.
`BACKUP_RETENTION_DAYS` and `BACKUP_RETENTION_MIN_COUNT` make it configurable. Cleanup is
dry-run by default and requires `BACKUP_RETENTION_APPLY=true` to remove files. It selects
only recognized, valid manifest/archive pairs contained directly in `BACKUP_DIR`, rejects
symlinks and path escapes, and never follows arbitrary paths. Orphans and malformed pairs
are reported for manual review rather than deleted.

Restore verification should run at least weekly in the deployment environment. CI runs a
small recovery cycle on every push/PR as code-level evidence, not as proof of a production
backup schedule.

## 10. Application-data retention boundaries

Backup-artifact retention is separate from application-record retention. Stage 23 adds no
product-data purge. It will not automatically delete AuditLog, approved AAR versions,
persisted AAR artifacts, document acknowledgements, incident evidence, operation records,
or historical crisis data. Business/legal retention periods are unknown and remain an
explicit deferred product/governance decision.

## 11. Integrity monitoring

`npm run integrity:check` will provide a bounded operational check with a configurable
row ceiling. It verifies:

- all repository migrations are recorded as successful and none are failed/incomplete;
- all PostgreSQL constraints are validated;
- approved AAR logical digests match canonical content;
- each inspected AAR PDF matches its recorded size and SHA-256, and its source digest
  matches the approved version;
- published internal-text Document versions match their content SHA-256;
- acknowledgement content-digest snapshots still match their referenced immutable
  Document versions when both values are present.

The command returns structured counts, elapsed time and failures, never protected content.
It exits non-zero on any invariant violation or if the configured bound is exceeded; it
does not silently validate an incomplete sample.

## 12. Operational health monitoring

Keep `/api/health` as cheap process liveness for compatibility. Add public
`/api/health/readiness` as a cheap technical dependency probe using one database query.
It returns 200 when PostgreSQL is reachable and 503 otherwise, with stable non-secret
JSON and no raw error. It does not run integrity scans or inspect organisational Readiness.

Backup, restore and integrity commands emit single-line JSON events and meaningful exit
codes suitable for cron, CI, log collection or another external monitor.

## 13. Failure alerting

The repository will not hard-code email, PagerDuty, Slack or another vendor. The external
scheduler/monitor must alert on a non-zero command exit, missing expected success event,
or stale last-success timestamp. Runbooks define that contract. A production deployment
should additionally alert when technical readiness returns 503 while liveness is 200.

## 14. Auditability

Every backup manifest records when and with which application/PostgreSQL/migration state
the artifact was created, its exact digest/size and critical counts. Operational commands
log event name, schema version, status, duration and safe artifact identifiers. The system
does not add recovery activity to product AuditLog because backup tooling may run while
the API is unavailable and must not mutate the source database merely to back it up.

## 15. Security considerations

- Connection URLs are required through environment variables and never logged or stored.
- Native clients receive connection components via `PG*` environment variables so the
  password is not placed on the command line.
- Backup artifacts contain sensitive operational data. Local permissions are a baseline;
  production storage must add access control, encryption at rest/in transit and off-host
  durability outside this repository.
- Temporary and published filenames are generated and path-contained. Restore refuses an
  active/nonempty target and retention refuses symlinks, invalid manifests and path escapes.
- Structured failures expose categories, not credentials, SQL content or record payloads.
- No production backup, user data, credential or generated artifact belongs in Git.

## 16. Configuration recovery

PostgreSQL-backed dictionaries, roles, permissions and other mutable configuration are in
the dump. Environment configuration (`DATABASE_URL`, Entra issuer/audience/JWKS, origin,
profile, ports, log/runtime worker settings), TLS certificates, DNS, network rules, images,
secret material and scheduler definitions are not. The restore runbook contains a checklist
to reconstruct these from the deployment's authorized secret/infrastructure systems.

`DATA_DIR` is not included because the current PostgreSQL production route composition has
no authoritative disk-backed product path. A deployment with out-of-contract durable files
must inventory and protect them separately before claiming this recovery objective.

## 17. Migration compatibility

The dump includes `_prisma_migrations`; restore verifies its exact completed identities
against the manifest and then runs the current application checker. CI always creates the
source from the complete migration chain. `pg_dump` must have a major version at least the
server major version; Stage 23 supports and tests PostgreSQL 16. `pg_restore` must share the
dump producer's major version for the verified path. Other versions require a successful
rehearsal before use. This logical workflow is not a major-version upgrade procedure.

## 18. Test strategy

- Unit: connection/config validation, manifest parsing, checksum, version compatibility,
  contained file resolution and retention selection/dry-run behavior.
- API: liveness compatibility, readiness success and sanitized database failure.
- PostgreSQL integration: bounded checker success plus intentional AAR PDF, AAR logical and
  Document digest corruption detection with test-only cleanup.
- Recovery: native dump, manifest verification, clean restore, migration/count/domain/hash
  verification and intentionally corrupted archive rejection.
- Regression: existing Stage 1–22 unit, PostgreSQL and browser suites remain authoritative.

## 19. CI implications

The normal PostgreSQL job will install/use PostgreSQL 16 client tools, expose a separate
administrative connection only to the CI service, and run `npm run test:recovery`. The
driver creates isolated databases so it does not share a database with API tests. It is a
required deterministic gate; fixture scale keeps the added runtime bounded. The production
startup step will also call the technical readiness endpoint. Existing quality, dependency
audit, browser and migration-rehearsal steps remain in place.

## 20. Operational runbooks

Create executable repository-specific procedures:

- `docs/runbooks/backup.md` — prerequisites, environment, backup, verification, schedule,
  retention and external monitoring contract;
- `docs/runbooks/restore.md` — incident checklist, empty-target provisioning, restore,
  verification, application startup and rollback/escalation boundary;
- `docs/runbooks/integrity-verification.md` — scheduled/on-demand checker, output, alerts
  and non-destructive diagnosis.

## 21. Explicit exclusions

Stage 23 does not implement Exercise, Training or organisational Readiness cleanup; Stage
24/25 product work; attachment upload; business data-purge policy; physical base backups,
WAL archiving or point-in-time recovery; cloud-provider infrastructure; cross-region
replication; secret-manager redesign; enterprise observability; PKI, signing or digital
signatures; or production capacity/load certification.

## 22. Definition of Done

Stage 23 is done when all 23 criteria in the task are evidenced: reproducible and
detectable backup; checksum/catalog manifest verification; clean non-destructive restore;
automatic meaningful recovery checks; corruption rejection; executable bounded integrity;
safe configurable retention; documented configuration boundary; liveness/readiness and
machine-readable command signals; executable runbooks; no embedded secrets; fresh migration
chain and all Stage 1–22/regression gates green; recovery in CI; no generated artifacts or
temporary databases left behind; and a complete implementation report.

## 23. Proposed commit sequence

1. `docs: define Foundation Stage 23 resilience plan`
2. `feat: add PostgreSQL backup and verification tooling`
3. `feat: add recovery integrity and technical readiness checks`
4. `feat: add safe backup retention tooling`
5. `test: automate Stage 23 recovery and corruption gates`
6. `docs: add resilience recovery runbooks`
7. `docs: record Foundation Stage 23 implementation`

Before every commit: inspect scope, run the relevant focused checks, and run
`git diff --check`. Full clean install, migration, unit, build, browser, PostgreSQL,
recovery, audit and production startup validation is required before Stage 23 may be
called complete or pushed for review.
